# Persistent Shell Sessions

## Overview

The AI Studio daemon now supports **persistent shell sessions** with automatic recovery that maintain state across commands within a single conversation. This allows natural shell workflows where directory changes, environment variables, and other shell state persist between commands.

**Key Features:**
- ✅ **State Persistence**: `cd`, `export`, working directory maintained across commands
- ✅ **Automatic Recovery**: Stuck sessions automatically detected and reset
- ✅ **Background Execution**: LLM can spawn long-running processes (dev servers) in parallel
- ✅ **Health Monitoring**: Sessions checked for responsiveness before command execution
- ✅ **Idle Cleanup**: Unused sessions cleaned up after 30 minutes

## How It Works

### Per-Conversation Scope

Each chat conversation in AI Studio gets its own isolated shell session:

```
Conversation A (SessionID: abc123) → Shell Session A
Conversation B (SessionID: xyz789) → Shell Session B
```

- **Isolated**: Commands in one tab don't affect another tab
- **Automatic**: No special syntax needed - just works
- **Cleanup**: Sessions are cleaned up when the conversation ends

### Stateful Commands

Commands that modify shell state are automatically routed through the persistent session:

**Directory Navigation:**
```
User: /c cd /tmp
AI: 📁 Changed directory to: /tmp

User: /c pwd
AI: /tmp
```

**Environment Variables:**
```
User: /c export MYVAR=hello
User: /c echo $MYVAR
AI: hello
```

**Session Management:**
```
User: /c status        # Check if a process is still running
User: /c stop          # Stop a long-running process
```

### One-Shot Commands

Simple queries that don't need state are executed as one-shot commands (faster):

```
User: /c ls -la        # Fresh execution, doesn't need session state
User: /c cat file.txt  # Fresh execution
User: /c git status    # Fresh execution
```

## Architecture

### Components

1. **Shell Session Manager** (`rag.go`):
   - Maintains map of `SessionID → shellSession`
   - Tracks working directory, running processes, environment
   - Provides `Run(sessionID, command, timeout)` interface

2. **Desktop Capability** (`desktop/capability.go`):
   - Routes slash-prefixed commands (`/c`, `/cmd`, `/shell`, `/exec`)
   - Detects stateful commands (`cd`, `export`, `status`, `stop`)
   - Chooses between persistent session vs one-shot execution

3. **Agent Integration** (`copilot.go`):
   - `InjectShellSessionManager()` wires up the session manager
   - Session manager injected when agent is created in daemon


## Session Lifecycle

### Creation

Shell sessions are created lazily on first command:

```
User opens AI Studio → SessionID generated by frontend
User types: /c cd /tmp → Shell session created for this SessionID
```

### Persistence

State persists for the lifetime of the conversation:

```
Tab open for 1 hour → Shell session alive for 1 hour
Multiple commands → Same session used
Refresh page → New SessionID → New session (fresh start)
```

### Cleanup

Sessions are automatically cleaned up to prevent resource leaks:

**Automatic Cleanup (Daemon):**
- Idle sessions older than **30 minutes** are closed
- Cleanup runs every **5 minutes**
- Background cleanup starts with daemon

**Manual Cleanup (User):**
- Browser tab closes → Frontend stops sending requests
- Page refresh → New SessionID generated → Fresh session
- Session expires → Resources released

**Background Sessions:**
- Spawned for parallel work (dev servers, watchers)
- Subject tsupports **background PTY sessions** for parallel work. This allows running long-running processes (dev servers, file watchers) in separate terminals while continuing work in the main session.

**LLM Integration:**

The coding workflow (execute_local_command tool) now supports a `background` parameter:

```json
{
  "tool": "execute_local_command",
  "command": "npm run dev",
  "background": true,
  "working_dir": "/path/to/project"
}
```

**When to Use Background:**
- ✅ Dev servers (npm run dev, python -m http.server)
- ✅ File watchers (npm run watch, webpack --watch)  
- ✅ Long-running builds (docker build, cargo build --release)
- ✅ Database servers (postgres, redis-server)

**The LLM automatically chooses** based on command patterns - you can also specify explicitly
- Can be explicitly closed via `stop` command

## Background Sessions

### Overview

The daemon can spawn **background PTY sessions** for parallel work. This allows running long-running processes (dev servers, file watchers) in separate terminals while continuing work in the main session.

### Use Cases

**1. Dev Server + Main Work:**
```bash
# Spawn background session for dev server
bgSessionID := SpawnBackgroundSession("/path/to/project")
Run(bgSessionID, "npm run dev &", timeout)

# Continue in main session
Run(mainSessionID, "npm test", timeout)
```

**2. Multiple Watch Processes:**
```bash
# Watch backend
bgSession1 := SpawnBackgroundSession("/backend")
Run(bgSession1, "npm run watch", timeout)

# Watch frontend  
bgSession2 := SpawnBackgroundSession("/frontend")
Run(bgSession2, "npm run watch", timeout)
```

### Background Session Lifecycle

```
SpawnBackgroundSession(workingDir) → Unique session ID (e.g., "bg-1234567890-0")
    ↓
Session created with isBackground=true flag
    ↓
Commands run in parallel with main session
    ↓
Subject to 30-minute idle timeout
    ↓
Explicit close or timeout → Resources released
```

### Session Limits

**Current Implementation:**
- No hard limit on concurrent sessions
- Idle cleanup prevents resource exhaustion
- Each session = one shell process

**Recommended Practice:**
- Keep background sessions minimal (1-3 max)
- Use for long-running processes only
- Clean up explicitly when done

## Phase 4: Parallel Execution Integration

### Overview

Phase 4 parallel execution extends the multi-turn orchestration architecture to run independent workflow steps concurrently. The PTY session architecture routes threads appropriately:

- **Main thread**: Uses PTY child process (preserves shell state)
- **Background threads**: Use exec.Command goroutines (stateless, parallel)

### Thread Routing Architecture

**Process Selection Logic** (`main.go:958`):
```go
func runLocalCommandWithWorkingDir(ctx, req) {
    // Main thread: Foreground + SessionID → PTY child process
    if !req.Background && req.SessionID != "" {
        return shellMgr.Run(req.SessionID, req.Command, timeout)
    }
    
    // Background threads: Background flag → exec.Command
    if req.Background {
        go runBackgroundJob(ctx, job, req)
        return jobID, nil
    }
}
```

**Context-Based Routing**:
```go
// Main thread (preserves session state)
Ask(ctx, "run tests")
  → sessionIDFromContext(ctx) → "session-123"
  → LocalCommandRequest{SessionID: "session-123", Background: false}
  → Routes to PTY child process ✅

// Parallel thread (stateless execution)
bgCtx := context.WithValue(ctx, "parallel_execution_mode", true)
Ask(bgCtx, "check formatting")
  → isParallelExecution(ctx) → true
  → LocalCommandRequest{SessionID: "", Background: true}
  → Routes to exec.Command goroutine ✅
```

### Example: Parallel Quality Checks

**Workflow**:
```
User: "Run tests and check formatting"
  ↓
AskParallel splits into 2 threads:
  
Thread 1 (Main):
  Query: "Run tests"
  SessionID: "session-123"
  Process: PTY child (preserves shell state)
  Working Dir: /project (from PTY session)
  Command: npm test
  
Thread 2 (Background):
  Query: "Check formatting"  
  SessionID: "" (stripped)
  Process: exec.Command goroutine
  Working Dir: /project (inherited from request)
  Command: npm run format:check
  ↓
Both execute in parallel
  ↓
Results aggregated
```

### Why This Design?

**Main Thread Uses PTY**:
- Preserves shell state (`cd`, `export`, etc.) for subsequent commands
- User's conversation continues with expected working directory
- Environment variables and aliases remain active

**Background Threads Use exec.Command**:
- Independent execution (no state dependencies)
- Clean process isolation
- Proper goroutine-based concurrency
- No PTY overhead for parallel work

**Benefits**:
- ✅ Main conversation context preserved
- ✅ Parallel work doesn't interfere with shell state
- ✅ Clean separation: stateful vs stateless execution
- ✅ Efficient resource usage (PTY only for main thread)

### Implementation Details

**Forcing Background Mode** (`copilottools.automation.go`):
```go
func (a *CopilotAgent) runLocalAutomationCommand(ctx, args, ...) {
    background := extractBackgroundFlag(args)
    sessionID := sessionIDFromContext(ctx)
    
    // Force background execution for parallel threads
    if isParallelExecution(ctx) {
        background = true
        sessionID = "" // Strip session to avoid PTY routing
    }
    
    request := LocalCommandRequest{
        SessionID:  sessionID,
        Background: background,
        Command:    command,
        // ...
    }
}
```

**Result**: Parallel execution is achieved with zero changes to PTY session management - routing happens automatically based on context flags.

**Cleanup Loop:**

```
Every 5 minutes:
    For each session:
        if (now - lastUsed) > 30 minutes:

```

**Safety:**
- Only idle sessions are cleaned
- Active sessions remain alive
- Cleanup runs in background goroutine

### Automatic Detection

Before executing each command, the daemon checks if the session is stuck from a previous command:

```go
if session.stillRunning {
    // Check health with echo command (2 second timeout)
    if !session.IsHealthy() {
        // Force reset: close stuck session, create fresh one
        log.Printf("PTY session %s unresponsive, forcing reset", sessionID)
        session.Close()
        session = newPTYShellSession(sessionID)
    }
}
```

### Health Check

The health check sends a simple echo command and waits for response:

```bash
echo __HEALTH_CHECK__
# Waits up to 2 seconds for output
# If no response → session is stuck
```

**Detection Criteria:**
- Session marked as `stillRunning` from timeout
- No response to health check within 2 seconds
- PTY read/write errors

### Recovery Process

**Automatic (Preferred):**
1. User command times out → `stillRunning = true`
2. Next command triggers health check
3. Health check fails → Session force-reset
4. Fresh session created with same sessionID
5. Command executes in clean environment

**Manual (API):**
```go
// Force reset without health check
shellMgr.ForceResetSession(sessionID)
```

**User-Initiated:**
```bash
# Send Ctrl+C to stuck command
User: /c stop
```

### When Recovery Happens

**Scenario 1: Long-Running Command Timeout**
```
User: /c npm install (times out after 600s)
System: Sets stillRunning=true, returns partial output

User: /c npm test
System: Health check fails → Reset session → Run test in fresh shell
```

**Scenario 2: Crashed Process**

```
System: PTY becomes unresponsive
```

**Scenario 3: Hung Interactive Prompt**
```

System: Timeout after 600s, stillRunning=true

User: /c git status
System: Health check hangs → Reset → Fresh session
```

## Implementation Details

### Stateful Command Detection

The `isStatefulCommand()` function checks if a command modifies shell state:

```go
func isStatefulCommand(cmd string) bool {
    trimmed := strings.TrimSpace(cmd)
    
    // Directory changes
    if strings.HasPrefix(trimmed, "cd ") || trimmed == "cd" {
        return true
    }
    
    // Environment variables
    if strings.HasPrefix(trimmed, "export ") {
        return true
    }
    
    // Session management
    if strings.EqualFold(trimmed, "status") || 
       strings.EqualFold(trimmed, "stop") {
        return true
    }
    
    return false
}
```

### Session ID Extraction

SessionID is extracted from the request context:

```go
func getSessionIDFromContext(ctx context.Context) string {
    if payload, ok := ctx.Value("session_payload").(*ai.SessionPayload); ok && payload != nil {
        if payload.SessionID != "" {
            return payload.SessionID
        }
    }
    return "default"
}
```

### Working Directory Tracking

The shell session maintains working directory state:

```go
type shellSession struct {
```

## Troubleshooting

### Session Not Persisting

**Symptom**: `cd` doesn't persist, `pwd` shows original directory

**Cause**: SessionID not being passed from frontend

**Fix**: Check that AI Studio frontend sends `X-SOP-Session-ID` header

### Cross-Tab State Leakage

**Symptom**: Commands in one tab affect another tab

**Cause**: Frontend sending same SessionID for multiple tabs

**Fix**: Frontend should generate unique SessionID per tab/conversation

### Stale State After Refresh

**Symptom**: After refresh, still in old directory

**Cause**: Frontend reusing old SessionID

**Fix**: Frontend should generate new SessionID on page load
